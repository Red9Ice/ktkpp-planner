# Техническое задание (ТЗ) на разработку системы автоматизации расписания для колледжа

## 1. Общие положения
- **1.1. Наименование проекта:** Интеллектуальная система составления и управления расписанием (Solver + Cloud-боты).
- **1.2. Цель проекта:** Автоматизация процесса генерации базового расписания на семестр, а также оперативного управления заменами (болезни/отгулы) для колледжа с более чем 25 группами.
- **1.3. Ключевое ограничение:** Система не должна требовать использования личного компьютера разработчика/пользователя в качестве постоянно работающего сервера (24/7) и не должна требовать покупки платного VPS.

## 2. Термины и определения
- **Группа** — учебная группа (например, 25-ИС).
- **Подгруппа (ПГ)** — часть группы (ПГ.1, ПГ.2), выделяемая для занятий в кабинетах с ограниченной вместимостью (компьютерные классы, лаборатории).
- **Пара** — учебный слот (1, 2, 3, 4, 5, 6).
- **Окно** — отсутствие занятия между парами в течение дня.
- **Whole-group занятие** — лекция или семинар, где вся группа должна присутствовать одновременно (синхронно).
- **Split-занятие** — занятие для одной подгруппы (лабораторная работа).
- **Solver (Решатель)** — математический движок, генерирующий расписание на основе ограничений.

## 3. Архитектура системы (Cloud/Serverless)
Система состоит из трёх независимых слоёв, размещённых на бесплатных облачных платформах:
1. **Слой данных (База данных):** Бесплатный облачный PostgreSQL (Supabase или Neon.tech). Хранение справочников и сгенерированных расписаний.
2. **Ядро (Backend / Solver):** Скрипт на Python с Google OR-Tools. Запускается по требованию (вручную на ПК диспетчера или через GitHub Actions), обрабатывает данные из БД и сохраняет результат обратно. Не работает 24/7.
3. **Слой интерфейсов (Боты):** Легковесные сервисы на Python, работающие 24/7 на бесплатных PaaS-платформах (Render.com или Koyeb). Боты работают через Webhooks, не потребляя ресурсы, когда к ним не обращаются. Обращаются к общей БД.

## 4. Функциональные требования

### 4.1. Управление данными (Справочники)
- **Группы и подгруппы:** Название, размер, список подгрупп.
- **Преподаватели:** ФИО, доступность, компетенции.
- **Кабинеты:** Номер, тип (лекционная, лаборатория, компьютерный класс), вместимость.
- **Учебная нагрузка:** Связка «Группа — Дисциплина — Преподаватель — Часы», тип занятия (whole-group или split).
- **Ограничения доступности:** Больничные, отгулы, ремонты кабинетов.

### 4.2. Логика работы с подгруппами и ограничения
- **Непрерывность (Contiguity) на уровне подгруппы:** Окна допустимы только в начале или конце дня. Если ПГ.1 учится на 1, 2, 3 парах, а ПГ.2 — на 3, 4, 5 парах, это считается допустимым. Внутри дня одной подгруппы окон быть не может.
- **Старт дня:** Занятия у подгруппы могут начинаться с 1-й, 2-й или 3-й пары (жёсткое ограничение `start <= 3`).
- **Окончание дня:** Жёсткое ограничение — не позже 6-й пары. Мягкое ограничение (штраф) — не позже 5-й пары.
- **Синхронизация:** Для whole-group занятий обе подгруппы должны быть свободны в один и тот же слот.
- **Split-занятия:** Могут проводиться параллельно (в двух разных кабинетах) или последовательно (в одном кабинете в разное время).

### 4.3. Режимы работы Solver
- **Full Generation:** Генерация с нуля на новый семестр.
- **Repair:** Корректировка существующего базового расписания (минимизация изменений).
- **Incremental Replacement:** Поиск замены для конкретного преподавателя без перестройки всего расписания.

### 4.4. Экспорт данных
- **Excel (.xlsx):** Сводные таблицы с объединенными ячейками для групп и подгрупп.
- **PDF (.pdf):** Сетки расписания для печати.
- **Текстовый формат:** Для вывода в чат-ботах.

### 4.5. Интерфейсы (Telegram и MAX боты)
- Функционал ботов идентичен.
- **Для диспетчера (Админ):** Команды на обновление данных, запуск Solver'а (через API GitHub Actions или напрямую), управление заменами.
- **Для студентов и преподавателей:** Получение расписания по команде (например, `/schedule 25-ИС`). Разделение вывода по подгруппам (ПГ.1 и ПГ.2), чтобы не было ложных «окон» в визуализации. Выдача файлов PDF/Excel.

## 5. Технический стек
- **Язык:** Python 3.11+
- **Solver:** Google OR-Tools (CP-SAT) — с использованием `AddAutomaton` для контроля непрерывности.
- **База данных:** PostgreSQL (Supabase / Neon).
- **Хостинг ботов:** Render.com / Koyeb (режим Webhooks).
- **Запуск Solver:** GitHub Actions (бесплатные раннеры) или локальный ПК диспетчера.
- **Telegram-бот:** aiogram 3 (асинхронный).
- **MAX-бот:** maxapi-sdk / maxogram.
- **Экспорт:** openpyxl (Excel), reportlab / weasyprint (PDF).

## 6. Этапы разработки (Roadmap)
- **Этап 1:** Инфраструктура и данные. Развертывание БД (Supabase), подготовка справочников одного семестра в CSV/JSON.
- **Этап 2:** Ядро Solver. Написание модели CP-SAT. Тестирование на 3-5 группах. Учет подгрупп, `start <= 3`, contiguity.
- **Этап 3:** Генерация артефактов. Модули экспорта в Excel, PDF и текст.
- **Этап 4:** Telegram-бот (MVP). Разработка и деплой на Render.com (Webhooks). Выдача расписания по запросу.
- **Этап 5:** Модуль замен. Логика Incremental Replacement.
- **Этап 6:** MAX-бот. Перенос интерфейса на платформу MAX.
- **Этап 7:** Автоматизация Solver. Настройка GitHub Actions для генерации расписания по кнопке из GitHub.

## 7. Критерии приемки (Definition of Done)
1. Solver находит валидное расписание для 25+ групп (время генерации — до 20 минут).
2. Отсутствуют жесткие конфликты (накладки преподавателей и кабинетов).
3. Правило непрерывности дня соблюдается для каждой подгруппы (ПГ.1 может учиться 1-3 пары, ПГ.2 — 3-5).
4. Система полностью автономна: после настройки облачных сервисов (Render, Supabase) личный ПК не нужен для работы студентов и преподавателей.
5. Боты корректно отдают расписание в тексте, PDF и Excel.
